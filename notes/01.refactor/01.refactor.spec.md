## Feature: 消除全局可变状态

**宪法依据**: 第4.2条 - "绝不允许使用全局变量来传递运行时状态，所有依赖必须通过函数参数或结构体成员显式注入（只读常量除外）"

**背景**:
当前代码中存在多处包级全局变量用于传递运行时状态，违反宪法的"不可协商"条款。
需消除的全局可变状态包括：
- `beans/init.go:15` 的 `startProcessTime`
- `consts.go:23-27` 的 `GitBranchName` 等5个变量（构建时注入，视为只读）
- `consts.go:30-32` 的 `subUnsubNames` 等3个切片（配置数据，应封装为不可变）
- `road/session_impl.go:25-26` 的 `globalIdGenerator`

**豁免**: 以下只读常量符合标准库实践，予以保留：
- `road/component/method.go` 的 `typeOfBytes`（反射类型缓存）

### Scenario: 进程启动时间通过依赖注入获取

```gherkin
Given 代码需要获取进程启动时间
When 创建依赖进程启动时间的组件
Then 启动时间应通过构造函数参数传入
And 不应从全局变量读取
```

### Scenario: Git编译信息通过构建参数传递

```gherkin
Given 代码需要展示版本信息
When 构建应用程序
Then Git信息应通过ldflags注入到结构体
And 不应使用包级可修改变量
```

### Scenario: Session ID生成器显式创建

```gherkin
Given 需要创建新的Session
When 初始化Session管理器
Then ID生成器应作为依赖传入
And 每个Session管理器实例拥有独立的生成器
```

## Feature: 显式错误处理

**宪法依据**: 第4.1条 - "所有错误或异常都必须被显式处理"

**背景**:
当前代码中存在多处错误被静默忽略的情况，需全部修复：
- `road/app.go:77-78` 网络写入错误仅跳过
- `road/app.go:97-99` 握手错误直接返回无日志
- `tools/file.go:25-27` 文件打开错误信息丢失
- `beans/command_deadlock_detect.go:39-40` 正则编译错误被忽略
- `topic.go:35` 仅打印错误未返回

---

### Scenario: 网络写入错误记录日志并返回

```gherkin
Given 向连接写入数据时发生错误
When 错误发生
Then 应记录详细错误日志
And 将错误返回给调用方
And 不应仅使用 continue 跳过
```

### Scenario: 握手失败返回具体错误原因

```gherkin
Given 新连接建立时需要握手
When 握手过程失败
Then 应返回包含失败原因的 error
And 调用方应能根据错误类型决策
```

### Scenario: 文件操作错误完整传递

```gherkin
Given 读取文件时发生错误
When 错误发生
Then 应将原始 error 包装后返回
And 调用方应能区分文件不存在/权限拒绝等不同原因
```

### Scenario: 编译期错误在初始化时处理

```gherkin
Given 正则表达式在 init 中编译
When 编译失败
Then 应在 init 中 panic 暴露问题
Or 将错误延迟到首次使用时返回
And 不应使用 _ 忽略错误
```

## Feature: 表格驱动测试

**宪法依据**: 第2.2条 - "单元测试必须优先采用表格驱动测试（Table-Driven Tests）的风格"

**背景**:
当前测试文件未采用表格驱动风格，需重构：
- `tools_test.go` 的 `TestNilToHtmlTable`
- `road/session_test.go` 的 `TestMakeFunc`
- `jwtx/jwt_test.go` 的 `TestSign`, `TestExpiration`
- `tools/file_test.go` 的 `TestReadFileTail`, `TestTimeSort`

---

### Scenario: 工具函数测试使用表格驱动

```gherkin
Given 测试 ToHtmlTable 函数
When 编写测试用例
Then 应使用 []struct{name, input, want} 定义测试表
And 应覆盖 nil、空切片、单元素、多元素等边界条件
And 使用 t.Run 为每个用例命名
```

### Scenario: Session测试覆盖多种场景

```gherkin
Given 测试 Session 的方法调用
When 编写测试用例
Then 应使用表格列出不同输入参数和期望输出
And 应包含正常场景和异常场景
And 不应为每个场景编写独立函数
```

### Scenario: JWT测试统一用例格式

```gherkin
Given 测试 JWT 签名和验证
When 编写测试用例
Then 应使用统一的测试表结构
And 包含有效token、过期token、无效签名等场景
And 每个场景在表格中清晰定义输入和期望
```

## Feature: Console结构体职责分离

**宪法依据**: 第4.3条 - "任何file, class, struct, method等代码实体都必须为单一目标设计"

**背景**:
`Console` 结构体（`console.go:30-38`）当前同时负责7个职责领域，违反单一职责原则。

---

### Scenario: Web服务生命周期独立管理

```gherkin
Given 需要管理Web服务的启动和关闭
When 设计服务管理组件
Then 该组件只负责生命周期管理
And 不应包含路由注册逻辑
```

### Scenario: 命令注册与执行分离

```gherkin
Given 需要注册和管理命令
When 设计命令系统
Then 命令注册器只负责注册
And 命令执行器只负责执行
And Console仅作为Facade协调二者
```

### Scenario: Topic管理独立封装

```gherkin
Given 需要管理Pub/Sub Topic
When 设计Topic组件
Then Topic管理应有独立结构体
And 通过接口与Console交互
And 不应直接操作Console内部状态
```

### Scenario: 认证状态由专门组件跟踪

```gherkin
Given 需要跟踪认证状态
When 设计认证系统
Then 认证状态应封装在AuthManager中
And Console通过接口查询状态
And 不应在Console中直接存储auth相关字段
```

## Feature: 简化反射使用

**宪法依据**: 第3.3条 - "简单的函数和数据结构优于复杂的接口和继承体系"

**背景**:
`road/component/` 包和 `session.receive.go` 存在过度使用反射的问题。

**决策**: 经评估，此问题涉及核心架构，重构风险高。根据YAGNI原则，当前功能正常且测试覆盖充分，**暂不修复**，留待未来版本考虑。

## 验收标准

| 功能 | 验收条件 | 验证方式 |
|------|---------|---------|
| 全局可变状态消除 | `grep -n "var [A-Z]" **/*.go` 无包级可变状态（反射类型缓存等只读常量除外） | 自动化脚本 + Code Review |
| 错误显式处理 | `grep -n "_ =" **/*.go` 无错误忽略（除io.Copy等明确场景） | Code Review |
| 表格驱动测试 | 每个测试函数使用 `[]struct{...}` 定义用例 | Code Review |
| 职责分离 | Console方法不超过5个，每方法不超过20行 | 静态检查 |
