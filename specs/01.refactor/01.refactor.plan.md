### 1.1 globalIdGenerator → Manager.idGenerator

**状态**: 待实施

**方案**: Manager持有ID生成器

**设计决策**:
- Manager负责生成Session ID，通过参数显式传递给newSession
- 使用 `atomic.Int64` 保证并发安全
- 每个Manager实例拥有独立的ID空间

**改动范围**:
- `road/manager.go`: Manager结构体添加idGenerator字段
- `road/manager.go`: NewSession方法生成ID并传递
- `road/session_impl.go`: 删除globalIdGenerator变量
- `road/session_impl.go`: newSession函数改为接收id参数

**代码变更**:

```go
// road/manager.go
type Manager struct {
    // ... 现有字段
    idGenerator atomic.Int64  // 新增
}

func (my *Manager) NewSession(link intern.Link) Session {
    var id = my.idGenerator.Add(1)  // Manager负责生成ID
    return newSession(my, link, id)  // 显式传入
}
```

```go
// road/session_impl.go
// 删除: var globalIdGenerator atomic.Int64

func newSession(manager *Manager, link intern.Link, id int64) Session {  // 新增id参数
    // ... 使用传入的id，不再自己生成
}
```

**验收标准**:
- `grep -n "globalIdGenerator" road/*.go` 无结果
- Session ID仍保持唯一递增
- `make test` 通过

### 1.5 typeOfBytes 等反射类型缓存 → 豁免

**状态**: **豁免保留**

**位置**: `road/component/method.go:19`

**豁免理由**:
- 根据宪法第4.2条修订，**只读常量**（如反射类型缓存）被明确允许
- 标准库广泛采用此模式（`encoding/json`、`fmt`等）
- 类型常量不可变，不会导致状态污染或测试困难
- 性能和可读性显著优于内联方案

**结论**: `typeOfBytes`、`typeOfError`、`typeOfContext` 等反射类型缓存作为**只读常量**保留，无需修改。

## P2: 错误处理修复方案

**对应规范**: Feature: 显式错误处理 (宪法第4.1条)

---

### 2.1 错误处理原则

**决策**:
1. **显式忽略原则**：若错误可以安全忽略，必须使用 `_ =` 显式忽略 + 注释说明原因
2. **分层处理**：
   - 边界层（网络IO）：记录日志 + 关闭连接 + 清理资源
   - 业务层（文件操作）：返回错误，让调用方决定
   - 初始化层（正则编译）：失败即panic（不可恢复）

### 2.2 具体修复点

#### 2.2.1 road/app.go 心跳写入失败

**决策**: 显式忽略 + 注释

```go
// 修改后
if _, err := conn.Write(heartbeatBuffer); err != nil {
    logo.Info("heartbeat write failed, addr=%s, err=%v", conn.RemoteAddr(), err)
    _ = conn.Close() // 显式忽略：commonLink.Close()永不为error，仅设置isClosed标志
    continue
}
```

#### 2.2.2 tools/file.go ReadTailLines

**决策**: 改为返回 error，破坏性变更

```go
// 修改前
func ReadTailLines(fullPath string, num int, filter string) []string

// 修改后
func ReadTailLines(fullPath string, num int, filter string) ([]string, error)
```

**待办**:

## P3: 表格驱动测试重构方案

**对应规范**: Feature: 表格驱动测试 (宪法第2.2条)

---

### 3.1 规范定义

#### 规范1: 测试用例结构

```go
func TestXxx(t *testing.T) {
    type args struct {
        // 输入参数字段
    }

    tests := []struct {
        name    string        // 测试场景描述
        args    args          // 输入参数
        want    Type          // 期望返回值（可选）
        wantErr bool          // 是否期望错误
        check   func(t *testing.T, got Type) // 可选：自定义验证
    }{
        {name: "正常路径", ...},
        {name: "空值输入", ...},
        {name: "边界条件", ...},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Xxx(tt.args...)
            if (err != nil) != tt.wantErr {
                t.Errorf("Xxx() error = %v, wantErr %v", err, tt.wantErr)
                return
            }
            if tt.check != nil {
                tt.check(t, got)
            } else if got != tt.want {
                t.Errorf("Xxx() = %v, want %v", got, tt.want)
            }
        })
    }
}
```

#### 规范2: 边界条件覆盖要求

每个被测函数至少覆盖：
- 正常路径
- 空值/零值输入
- 无效输入（空字符串、负数、nil等）
- 边界值（最小/最大值）

#### 规范3: 外部依赖处理

**文件系统依赖**：使用 `os.CreateTemp` 创建临时文件，确保测试可重复

## P4: Console职责拆分方案

**对应规范**: Feature: Console结构体职责分离 (宪法第4.3条)

---

### 4.1 拆分方案

**状态**: 已决策

**决策**: 采用三大组件方案，Console保留为Facade，保持向后兼容

### 4.2 目标架构

```
┌─────────────────────────────────────────────┐
│              Console (Facade)               │
│  - 保持现有公共API不变                        │
│  - 内部委托给各Manager组件                    │
├─────────────────────────────────────────────┤
│  CommandManager      │  TopicManager        │
│  - 命令注册          │  - Topic注册          │
│  - 命令查找          │  - 订阅管理           │
│  - 内置命令管理       │  - 定时推送           │
│  (原commands sync.Map)│  (原topics sync.Map)  │
├─────────────────────────────────────────────┤
│           Web/Session管理层                  │
│  (直接使用*road.App，不额外封装)              │
└─────────────────────────────────────────────┘
```

### 4.3 Console公共API保持不变

以下方法保持签名不变，仅内部实现调整：

```go
func NewConsole(mux IServeMux, opts ...ConsoleOption) *Console
func (c *Console) RegisterService(name string, service component.Component)
func (c *Console) RegisterCommand(cmd *Command)
func (c *Console) RegisterTopic(topic *Topic)
func (c *Console) GPID() string
func (c *Console) BaseUrl() string
func (c *Console) App() *road.App
```

### 4.4 内部重构细节

**CommandManager组件**：

```go
type CommandManager struct {
    commands sync.Map // 原Console.commands
}

func (m *CommandManager) Register(cmd *Command)
func (m *CommandManager) Get(name string) ifs.Command
func (m *CommandManager) GetAll() []ifs.Command
func (m *CommandManager) RegisterBuiltins(port int)
```

**TopicManager组件**：

```go
type TopicManager struct {
    topics sync.Map // 原Console.topics
}

func (m *TopicManager) Register(topic *Topic)
func (m *TopicManager) Get(name string) *Topic
func (m *TopicManager) GetAll() []ifs.Command
func (m *TopicManager) RegisterBuiltins()
```

**Console作为Facade**：

```go
type Console struct {
    options      consoleOptions
    app          *road.App
    gpid         string
    baseUrl      string

    // 内部组件
    commandManager *CommandManager  // 替代commands sync.Map
    topicManager   *TopicManager    // 替代topics sync.Map

    lastAuthTime atomic.Value
}

// RegisterCommand 保持API不变，内部委托
func (c *Console) RegisterCommand(cmd *Command) {
    c.commandManager.Register(cmd)
}
```

### 4.5 实施步骤

1. **创建CommandManager**：提取commands相关逻辑
2. **创建TopicManager**：提取topics相关逻辑
3. **调整Console**：改为持有Manager组件，保持公共API
4. **验证兼容性**：确保现有调用方无需修改

### 4.6 注意事项

- **零破坏性**：所有公共方法签名保持不变
- **逐步迁移**：可先实现CommandManager，再实现TopicManager
- **测试先行**：为Manager组件编写单元测试，再重构Console

## P5: 反射体系简化

**对应规范**: Feature: 简化反射使用 (宪法第3.3条)

---

**状态**: 已决策 - 保持现状

**决策**: 暂不改动

### 5.1 现状分析

`road/component/` 包使用反射进行：
- 方法自动发现（`ExtractHandler`）
- 动态方法调用（`Method.Func.Call`）
- 回调函数创建（`reflect.MakeFunc`）

### 5.2 保持现状的理由

1. **风险收益比**：反射体系是框架核心，改动影响面广
2. **稳定性**：当前运行稳定，无已知问题
3. **优先级**：P1-P4已满足主要宪法要求
4. **未来规划**：如后续出现性能瓶颈，再考虑代码生成方案
